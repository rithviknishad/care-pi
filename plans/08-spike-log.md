| `MemoryMax` **enforcement**: 100 MB allocation inside a 64 MB unit | **Only killed once `MemorySwapMax=0` was also set** (`oom_kill 1`, rc 137). With the default (`MemorySwapMax=infinity`) the allocation succeeded by spilling into zram swap. |
| `systemctl stop sp2-pod.service` then `start sp2-web.service` | Chain comes back; but stopping the *pod* unit first leaves the container units in `failed` (they are killed from under systemd) |

Design consequences:

1. **Set both `MemoryMax=` and `MemorySwapMax=`** on every container unit, or `MemoryMax` is a
   soft cap in practice. Proposal: `MemorySwapMax` = 0 for Postgres and Redis (they must not
   page), a small allowance for the API/worker units, and generous for the FE builder (its
   peak is short and swap is zram). Tune in SP3/SP4.
2. **Lifecycle goes through a `care.target`**, never the pod unit directly: `care.target`
   `Wants=` every container unit; the agent stops containers (reverse order) before the pod.
   Container units get `PartOf=care.target` so `systemctl stop care.target` is clean.
3. The `.build` unit works and is cached, so P15's local-build override needs no shell-outs.
4. Stock Pi OS `cmdline.txt` has `cgroup_disable=memory`; lumine only has the controller
   because a `cgroup_enable=memory` was appended earlier. **The image (P18) and `install.sh`
   must ensure `cgroup_enable=memory cgroup_memory=1`** — without it every `MemoryMax` above
   is silently ignored. Added to the installer checklist.

### Findings

1. **Memory is not the limiter on a 2 GB Pi 5; CPU is.** One sync gunicorn worker saturates
   roughly one core; throughput scales almost linearly 1→2 workers (54→93 req/s) and only +22 %
   for 2→3 because the load generator, Postgres and celery share the four cores. Even `solo`
   serves ~50 simple API req/s — a 2–4 staff clinic issues single-digit req/s.
2. **The `api` cap must scale with the worker count**: ≈ 64 MiB + 200 MiB × workers. `busy`
   with 3 workers sits *on* a 512 MiB cap (no OOM only because reclaim kept up). Recommended
   `MemoryMax` / `MemorySwapMax`: `solo` 320M/64M, `small-clinic` 512M/128M, `busy` 768M/128M.
   Worker: 384M/128M at concurrency 1, 512M/128M at 2. Beat: 384M/128M (migrate is its
   peak). db 384M/0 (512M/0 when `shared_buffers=256MB`), redis 96M/0, versitygw 128M/0.
3. **Headroom for the FE build.** With `small-clinic` idle the host has ~960 MiB available;
   the builder wants 1 GiB (S8). Scaling to `solo` and stopping `worker` frees ≈ 350 MiB
   (api 343→230, worker 234→0) → ~1.3 GiB available. Confirm in SP4. With `busy` on 2 GB
   only ~700 MiB is free at idle, so `busy` **must** scale down for builds and should be
   console-warned on 2 GB (keep "recommended on 4 GB+" in §8 of `01`).
4. **The write `400`s are a Care behaviour, not a Pi one.** `PatientViewSet.perform_create`
   takes a global non-blocking Redis lock (`care/emr/locks/billing.py` `PatientCreateLock`,
   `care/utils/lock.py` → `cache.set(nx=True)` else `ObjectLocked`) and returns `400 "Patient
   creation failed, try again after a while"` when two creates overlap. With 1 worker: 0/100
   failed; 2 workers: 8/100; 3 workers: 35/100 — purely a function of overlap in our
   unrealistic back-to-back writer loop. Any multi-worker Care deployment behaves the same. Not
   ours to fix; just **never use parallel creates in agent health probes.**
5. `ab`'s "Failed requests" on list endpoints are length mismatches (the list changes under
   concurrent writes), not errors; `Non-2xx` was 0 in every run.
6. Care access JWTs live **10 minutes**; anything the agent does against the API (synthetic
   checks, first-admin creation) must re-login rather than cache a token.
7. `load_fixtures` is unusable in the production image (no `faker`); demo data for the
   onboarding "try it" path needs its own small seeder via the API.
8. Not measured: Pi 4 (expect ~2–3× lower CPU throughput — *inference*; same memory figures),
   Caddy and the agent (SP7 / Phase 1), pgBackRest during backup (SP6).

### Findings

1. **S8's "≈ 1 GB" was wrong for today's care_fe.** The vite 8 / rolldown build has an
   anonymous working set of **≈ 1.8–2.0 GiB** (RSS + swap at peak), largely outside the V8 heap
   (rolldown/oxc are native), so `--max-old-space-size` does not bound it. A hard 1 GiB cap with
   512 MiB swap is killed every time, with or without sourcemaps.
2. **It still fits a 2 GB Pi — because of zram.** Pi OS trixie's `rpi-swap` provisions a
   zram device sized 1× RAM (zstd) with a `/var/swap` writeback file; the build's cold pages
   compress ≈ 4:1, so the whole thing costs ≈ 0.8 GiB RSS + ≈ 0.25 GiB of zram. Build time is
   barely affected (68 s vs 55 s with no pressure).
3. **Shape the builder, don't cap it.** The winning unit settings are
   `MemoryHigh=768M` (throttle + reclaim the builder *first*), `MemoryMax=1700M`,
   `MemorySwapMax=1500M`, `OOMScoreAdjust=900`. This kept host `MemAvailable` ≥ 370 MiB and API
   latency at 15–30 ms mean throughout, versus 147–209 MiB free when the builder was left to
   grab RAM first. If the host still runs out, the kernel picks the builder (score 900), not
   Postgres. Pair this with `OOMScoreAdjust=-500` on `care-db`/`care-redis` (both already
   `MemorySwapMax=0`, so they stay resident).
4. **Scale-down stays** (api → 1 worker, worker stopped: frees ≈ 350 MiB). The API never
   stalled during any build (max single probe 0.37 s, zero probes > 1 s), so S8's "no API
   downtime" holds. Not tested: building *without* scaling down — don't.
5. **Sourcemaps off by default** for on-Pi builds: 30 % faster, 13 MB instead of 45 MB served,
   ~10 % less memory; operators can opt in (useful only for error reporting). Pass
   `--sourcemap false` on the CLI; no upstream patch.
6. **Cold build ≈ 3 min, warm ≈ 1 min on Pi 5.** Keep `node_modules` (1.2 GB) and the npm
   cache (0.4 GB) on a persistent per-repo build dir: `npm install` against an unchanged
   lockfile is seconds; a changed lockfile reuses the cache. Budget ≈ 2 GB of disk per FE
   repo (care_fe + each locally built FE plug). Source comes from the GitHub tarball endpoint
   (`codeload.github.com/<org>/<repo>/tar.gz/<sha>`, 21 MB) — no git in the builder image, and
   a tracked branch is just "resolve ref → sha via the API, then fetch the tarball".
7. Pi 4 2 GB: not measured. Expect 2–3× longer (CPU-bound: 2–3 min CPU time on Pi 5) and the
   same memory shape; zram is slower there too. The `artifact` provider is the safer default
   on Pi 4 (*inference*; confirm when a Pi 4 is available — see O11).
8. Image/installer requirements that fall out of this: **zram must be on and sized ≥ 1× RAM**
   (Pi OS default via `rpi-swap`; `install.sh` must check it on other distros and refuse or
   set up `systemd-zram-generator`), `vm.swappiness` left at Pi OS's 60, and the memory cgroup
   controller enabled (SP2).

### Findings

1. **Region must match or nothing works**: Care defaults `BUCKET_REGION=ap-south-1`,
   versitygw defaults `us-east-1` → `AuthorizationHeaderMalformed` on every call. Render
   `VGW_REGION` from the same value. `CreateBucket` then needs `LocationConstraint` (plain
   `create_bucket` returns `IllegalLocationConstraintException` for a non-`us-east-1` region).
2. **Care never creates buckets** (grep: only `put/get/delete_object`). `care-pi apply` creates
   both buckets and applies the facility-bucket read policy; it must be idempotent.
3. Presigned URLs carry the canonical host; Caddy must proxy them **without rewriting path or
   Host** (both are signed). Caddy's `reverse_proxy` default already preserves both.
4. `tls internal` for an IP site works, but **`default_sni <ip>` is mandatory**. Since the LAN
   IP can change, the agent re-renders the Caddyfile on NetworkManager address changes.
5. **Port conflict class**: `tailscale serve` on lumine binds `<tailnet-ip>:443`, which makes
   a `0.0.0.0:443` publish fail (`address already in use`) and the pod unit flap. Publish on
   explicit LAN addresses; the agent detects and reports conflicts; care-pi's Tailscale
   integration goes through Caddy (`tailscale` cert getter / listener), never `tailscale serve`.
6. **mDNS observations (feed SP8)**: (a) on the Pi itself `lumine.local` resolves to
   `10.88.0.1` — the **podman0 bridge** — via nss-mdns, while LAN clients correctly get the
   eth0 IPv4 + the IPv6 ULA (avahi answers per interface). Set
   `allow-interfaces=eth0 wlan0` in `avahi-daemon.conf` and never let the agent resolve its own
   name. (b) **`care.local` already exists on this LAN** (another device, `192.168.165.117`).
   Name collisions are real; avahi renames to `care-2.local`, so the console and the
   printed/QR first-contact material must show the *actual* advertised name and IP, not assume
   `care.local`.
7. versitygw `MemoryMax` should be 256M, not 128M (79 MiB peak on one 50 MB transfer; a
   few concurrent uploads would hit 128M). Caddy's 96M is ample.
8. Django behind Caddy: pass `X-Forwarded-Proto`; set `CSRF_TRUSTED_ORIGINS` to every served
   origin (admin/session forms), `DJANGO_ALLOWED_HOSTS` to the served hostnames + IP.
   Upstream's static prefix is `/staticfiles/` (whitenoise), not `/static/`.
9. Multihost caveat stands: `BUCKET_EXTERNAL_ENDPOINT` is one value, so presigned URLs always
   name the canonical host; with > 1 hostname the `care_multihost_files_be` plug (or a Caddy
   rewrite that re-signs — not possible, SigV4) is required, as already decided.

### Findings

1. **Multi-repo archive-push is all-or-nothing, so one dead destination breaks RPO for every
   destination.** With repo3 unreachable: each `archive-push` spends ~121 s retrying repo3
   (`12 retries from 105-60000ms`, `io-timeout` 60 s), then returns failure; Postgres keeps the
   segment `.ready`, retries it every minute, and **does not advance to later segments** — repo1
   received 2 segments in 4 minutes while 8 were produced; `pg_wal` grew to 145 MB; the async
   worker logs "stopped archive-push after an error, remaining WAL will be processed on the
   next run". When repo3 returned, everything caught up in < 15 s. This directly contradicts
   `02` §3's "a slow or offline off-site repo does not stall Postgres": `archive-async` hides
   *latency*, not *failure*. Backups are also per-repo: `pgbackrest backup` without `--repo=N`
   writes **only repo1** (`info` showed repo2/3 "no valid backups"); each repo needs its own
   `backup --repo=N` run, and a failing one fails independently. Consequence for the design:
   **pgBackRest owns exactly one repo (local, encrypted); off-site copies are a separate,
   per-destination, failure-isolated tier.** Settled as **S40** (`00`, `02` §3): restic
   snapshots of the encrypted repo1 + files + config to each destination, with no shared
   failure domain and no Postgres coupling.
2. **SFTP host-key pinning**: libssh2 negotiated **ECDSA**, not ed25519, so the fingerprint
   must be the one pgBackRest reports (`host [<sha256>] and configured fingerprint … do not
   match`) — TOFU in the wizard: run `check` once, show the reported fingerprint and key type,
   store it. Key format: RSA PEM worked first time; don't assume OpenSSH-format ed25519.
3. **Bind-mount directories, not files.** Editing `pgbackrest.conf` with `sed -i` replaced the
   inode; the container kept the old one until restart. The renderer must write
   `/etc/care-pi/rendered/pg/` and mount the directory (atomic rename inside it is then visible).
4. Neither pgBackRest nor Care creates buckets: the agent creates the backup bucket as it
   does the Care ones. Non-`us-east-1` regions need `LocationConstraint`.
5. `--repo=N` restores stream directly from SFTP/S3 (no local staging) — the restore path
   from an off-site pgBackRest repo is excellent, which was the one argument for keeping an
   off-site destination *as* a pgBackRest repo (the rejected Option B in `02` §3).
6. Restarting `care-db` alone left `care-api`/`care-worker` `failed` until `care.target` was
   started again (Requires chain through beat). The agent restarts the stack via the target,
   never a single unit, and `Restart=always` + `RestartSec` stay on every unit as a backstop.
7. versitygw stores object metadata in **xattrs** (`user.etag`, `user.content-type`,
   `user.checksums`); any file-level copy of `/var/lib/care-pi/s3` must preserve xattrs (restic
   does on Linux; plain rclone/rsync-to-S3 does not) — or run versitygw with `--sidecar`.
8. Sizing: with `archive_timeout=300`, an idle clinic produces one 16 MB segment (≈ 1 MB
   zst) every 5 min ≈ 300 MB/day of compressed WAL at worst; `repo1-retention-full=2` +
   weekly fulls bounds the local repo to roughly 2× DB + 2 weeks of WAL. The S3 and SFTP
   `verify` cost (full read-back) argues for verifying off-site copies by *sampling*
   (`restic check --read-data-subset`) rather than `pgbackrest verify` on remote repos.
9. **Postgres crash-restarted because `archive-push` was killed and the container had no
   init.** During the outage test one `archive_command` hit pgBackRest's 60 s async
   timeout (`[082]`); the next one ended with *"archive command was terminated by signal 3:
   Quit"* → `server process exited with exit code 39` → postmaster terminated all backends and
   ran crash recovery (no OOM involved; `memory.events` all zero). Postgres as PID 1 in a
   container does not reap orphaned grandchildren, and pgBackRest's async worker is exactly
   such a detached grandchild. Reproduced on demand with `podman exec care-db sh -c '( sleep 2;
   exit 39 ) & exit 0'` → reinitialising every time; with **`RunInit=true`** (catatonit as PID 1)
   the same command causes no reinit. **Every container unit gets `RunInit=true`** —
   cheap and removes a whole class of surprises (same for gunicorn/celery children).
10. **`systemctl stop care.target` returns before PartOf-propagated stops finish** (0 s;
    units still `deactivating`), and a `start` issued meanwhile replaces the pending stop job —
    `care-db` silently kept running with the old config/image. The agent must stop the target,
    then wait for every unit to be `inactive` (or stop the units explicitly, in reverse order)
    before starting again. Full cold restart of the whole stack from an already-migrated DB:
    **44 s**.

### Findings

1. **Fixed — the first apply stopped at `start-target`.** `systemctl reset-failed <units>` exits
   with code 1 and `Unit care-pod.service not loaded.` for each unit: `daemon-reload` generates

   `agent/internal/host/host_test.go`. The second `bootstrap` continued from the partial state
   (`care.target is not active` → start) without manual work.
2. **Fixed — the rpi-swap drop-in did not remove the 2048 MiB limit.** `rpi-systemd-config`
   (rpi-swap 1.2.4) drops an empty `MaxSizeMiB=`, and `rpi-desired-zram-size` then uses its
   default 2048. On a Pi with more than 2 GB, the installer asks for a reboot, and the next run
   stops with "zram swap is not active, but its configuration exists". Fix:
   `installer/install.sh` writes `MaxSizeMiB=65536`. A test file in `/run/rpi/swap.conf.d` on
   lumine gave 4048 → 4048 MiB and 8064 → 8064 MiB (empty value: 2048). A real install on a

3. **Fixed — warm FE builds became cold builds.** The warm path (`npm install`) rewrites
   `package-lock.json` (probably for the platform packages that the `postinstall` of care_fe
   adds). The next build of the same source then saw a different hash and ran `npm ci` (101 s
   instead of 7 s). The stored hash was then the hash of the changed file, so a new care_fe sha
   with the same lock also ran `npm ci`. Fix: `quadlets/templates/fe-build.sh.tmpl` keeps the
   lock of the source in `.care-pi-package-lock.json` and copies it back before npm; 3 goldens;
   `docs/fe.md`. Verified: re-fetch (`npm ci`), then 2 builds with `npm install` (7 s, 6 s).
